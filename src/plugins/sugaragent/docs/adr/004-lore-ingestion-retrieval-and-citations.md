# ADR-SA-004: Lore Ingestion, Retrieval, and Citations

## Status

Proposed

## Context

LLM dialogue must stay grounded in project lore and avoid uncontrolled hallucination.

## Decision

### 1) Authoritative lore source

Use a dedicated markdown lore repository as the source of truth.

Recommended:

1. Lore is authored in markdown files.
2. Lore lives in its own GitHub repo (for example `game-lore-wiki`).
3. SugarEngine/SugarAgent does not edit canonical lore at runtime.

This gives clean ownership and revision history independent of runtime code.

### 2) Authoring format

Each lore page is one markdown file with required frontmatter metadata.

Example frontmatter:

```yaml
id: lore.town.founding
title: Founding of Valle Fresca
canon_level: hard
entity_ids: [npc.mayor_alba]
location_ids: [loc.valle_fresca]
faction_ids: [faction.council]
time_period: post-war
```

Required metadata:

1. `id`
2. `title`
3. `canon_level` (`hard`, `soft`, `rumor`)

Optional metadata:

1. `entity_ids[]`
2. `location_ids[]`
3. `faction_ids[]`
4. `time_period`
5. `tags[]`
6. `beat_ids[]` (optional mapping to authored story-beat identifiers)

Important boundary:

1. `beat_ids` are optional retrieval hints only.
2. Beat objectives, completion rules, and progression authority remain in scripted quest/episode data.
3. SugarAgent must never treat wiki `beat_ids` as canonical beat definitions.

### 3) Import model into SugarAgent

SugarAgent imports lore from a pinned repo snapshot, not from a floating branch.

Implementation rule:

1. Lore source is referenced by URL + commit SHA.
2. Ingestion runs against that exact snapshot.
3. Build artifacts include source provenance.

Suggested lock file in plugin:

- `src/plugins/sugaragent/lore/lore-source.lock.json`

Example shape:

```json
{
  "repo": "git@github.com:org/game-lore-wiki.git",
  "commit": "abc123...",
  "ref": "refs/tags/v0.4.0"
}
```

### 4) Ingestion pipeline

Add a deterministic ingestion command:

```bash
npm run sugaragent:lore:ingest -- --source <path-or-repo> --commit <sha>
```

Pipeline stages:

1. Parse markdown + frontmatter.
2. Chunk by heading/section.
3. Build retrieval metadata index.
4. Build embedding vectors (local embedding provider).
5. Emit generated artifacts for runtime loading.

Suggested output path:

- `src/plugins/sugaragent/lore/generated/`

Generated manifest must include:

1. source repo URL
2. source commit SHA
3. generation timestamp
4. ingestion tool version

### 5) Retrieval and citations

Use retrieval before generation:

1. metadata filters (entity/location/faction/time)
2. keyword/entity hits
3. active beat filter/boost when an authored beat contract is present
4. vector similarity ranking

Beat context source of truth:

1. Active beat context comes from engine-authored quest/episode contracts.
2. Lore `beat_ids` only assist ranking when present; they do not define or mutate beat state.

Citations in model output must map to generated chunk IDs that resolve back to:

1. source markdown file path
2. section heading
3. source commit SHA

When active beat contracts provide required facts, retrieval should prioritize lore chunks that best support those facts first.

### 6) Conflict precedence

Resolve lore claims with this precedence:

1. live world state
2. active quest/script state
3. hard canon lore
4. soft lore / rumors
5. model inference

### 7) Branching and release policy

Recommended lore repo policy:

1. protected `main` branch
2. PR review required for canon changes
3. version tags for release snapshots used by game builds

Game builds should only ingest tagged or explicitly pinned commits.

### 8) Future remote sync model (post-MVP)

Remote lore updates should be supported as **data updates**, not code/plugin updates.

High-level approach:

1. Author lore in the dedicated git repo as above.
2. CI builds versioned lore artifacts from tagged/pinned commits.
3. Artifacts are published to a secure update origin (API or CDN fronted by API).
4. App checks for a signed update manifest at startup (or scheduled intervals).
5. If a newer compatible lore package exists, app downloads and verifies it, then atomically activates it.
6. If verification fails, app keeps the existing local lore package and remains fully offline-capable.

Recommended security rules:

1. Use TLS for transport.
2. Manifest and package must be signed (detached signature or equivalent).
3. Package hash must match manifest hash before activation.
4. Include compatibility fields (`minPluginVersion`, `maxPluginVersion`, `schemaVersion`).
5. Keep the last known-good lore package for rollback.

Recommended packaging shape:

1. `manifest.json` (version, commit SHA, signatures, compatibility, URLs)
2. `lore-package` (chunk/index artifacts generated by ingestion)

Operational notes:

1. Fronting git with an API/CDN is preferred for client simplicity and security controls.
2. iOS/Android/Desktop app stores allow this because lore packages are content/data, not executable code.
3. Plugin and runtime binaries still update through normal app release process.

## Consequences

Positive:

- Better factual consistency.
- Inspectable provenance for lore claims.
- Clear authoring workflow for narrative team.
- Clean separation between canonical lore and runtime behavior.

Tradeoff:

- Ingestion/indexing pipeline adds maintenance cost.
- Requires lore release discipline (pinning/versioning).
- Remote sync adds operational/security complexity in exchange for live lore updates.

## MVP Test (End of Phase 2)

1. Create/update one markdown lore page in the lore repo.
2. Pin commit in `lore-source.lock.json`.
3. Run ingestion command.
4. Run sim question against that lore.

```bash
npm run sugaragent:lore:ingest -- --source ../game-lore-wiki --commit <sha>
npm run sugaragent:sim -- --npc librarian --ask "Who founded this town?"
```

Expected:

- Response includes citation references.
- Citation points to generated local chunk IDs.
- Chunk IDs resolve to markdown source file + section + commit SHA.
- If beat context is provided, retrieved chunks should align with beat-required facts when available.
